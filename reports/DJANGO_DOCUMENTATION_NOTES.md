# BiteTracker Django Migration: Notes for Chapters 4 and 5

Verified facts about the implemented system as of 6 October 2026, for updating the design/implementation (Chapter 4) and testing/results (Chapter 5) chapters. Detailed logs: `MIGRATION_NOTES.md`. Test evidence: `reports/SPRINT_II_TESTING.md`.

## 1. What changed

- The user interface moved from **Streamlit** (a prototype with no authentication) to **Django 5.2.17 (LTS)** with Django templates, Bootstrap 5 and Plotly.
- The ML pipeline (`src/`, `scripts/train_models.py`) was **not** redesigned. Preprocessing, the 20 features, the chronological split, TimeSeriesSplit validation, model selection by validation MAE (RMSE tie-break), the naive baselines and final test isolation are unchanged.
- The only change inside `src/` that affects behaviour: the decision-support model label now comes from the saved model metadata. It previously defaulted to "Tuned XGBoost" even though Random Forest was selected. Other `src/` edits were docstring wording only.

## 2. Final architecture

Layered architecture:

1. **Presentation:** Django templates (`templates/`), Bootstrap 5.3.3, Bootstrap Icons 1.11.3, plotly.js 3.7.0 (all from CDN), `static/css/bitetracker.css`.
2. **Web/application layer:** Django apps
   - `web/accounts`: authentication URLs
   - `web/core`: views, forms, charts, user-facing error messages
   - `web/schools`: models, admin, upload views, `import_schools` command
   - Views are thin: they validate input with Django forms and call services.
3. **Service layer:** `services/` contains plain Python with no Django imports, verified by a test:

   | Module | Responsibility |
   |---|---|
   | `data_service` | historical data from the processed CSV |
   | `model_service` | lazy, cached, verified model loading |
   | `forecast_service` | forecast + planning orchestration |
   | `performance_service` | saved metrics |
   | `upload_service` | upload validation |
   | `status_service` | data label |
   | `calendar_service` | school calendars |

   A REST API or another frontend could reuse these modules.
4. **ML / domain layer:** existing `src/` modules (forecasting, feature building, decision support, budgeting, resource allocation, data validation).
5. **Artifacts:** `models/final_best_model.joblib` and its metadata, `data/processed/school_meals_processed.csv`, and `reports/metrics/*.csv`. All are generated by `scripts/train_models.py` and git-ignored.

**Request flow for a forecast:** browser POST (CSRF token) → `ForecastForm` → `forecast_service.generate_forecast` → `data_service` (school history) → `model_service.get_model()` (loaded once per process, verified) → `src.forecasting.forecast_school_demand` (existing feature building + prediction) → `src.decision_support.build_decision_support_result` → `src.budgeting.estimate_meal_cost` / `src.resource_allocation.compute_allocation` → `ForecastRun` saved → redirect to result page (POST/redirect/GET).

## 4. Database design (Django ORM, migration `schools.0001_initial`)

Historical meal-demand records are **not** stored in the database. The processed CSV remains the single source of truth for the ML pipeline.

| Model | Purpose | Key fields |
|---|---|---|
| `User` (`django.contrib.auth`) | Accounts, staff flag, permissions | — |
| `School` | School metadata | `school_id` (unique, stable), `name`, `county`, `sub_county`, `verified_enrolment` (nullable; entered by admins only; not a model feature), `data_source`, `is_active`, timestamps |
| `DatasetUpload` | Record of each validated upload | `uploaded_by`, `original_filename`, `file` (valid files only), `file_size`, `uploaded_at`, `validation_status` (valid/invalid/unreadable), `forecast_readiness`, `n_records`, `quality_score`, `validation_summary` (JSON aggregates only), `processing_status` (always "not processed") |
| `ForecastRun` | Audit record of each forecast | `user`, `school` (optional FK) + `school_code`/`school_name`, `horizon_days` (1/7/30), `origin_date`, `first`/`last_forecast_date`, `assumptions` (JSON), `model_label`, `model_version` (training timestamp), `results_label`, day-1 predicted/recommended/risk, horizon totals, `result_summary` (JSON per-day results) |

`import_schools` fills `School` from the active dataset. It is idempotent (matched on `school_id`) and reports created/updated/unchanged counts.

## 5. Model integration

- **No training at startup or during requests.** The saved model is loaded on the first forecast and cached per process. The cache is keyed on file modification times, so a re-run pipeline is picked up automatically.
- **Verification before use.** The model must match its metadata in estimator class, scalar hyperparameters and target variable. The model, the metadata and `feature_columns.json` must all list the same 20 features, in the same order, as inference builds. Any mismatch stops the forecast with a clear error.
- **Parity.** Forecasts through the service layer are exactly equal to calling `src.forecasting` directly (18 real-model cases and 6 stub cases). Django and the former Streamlit page gave identical forecasts for the same inputs at all three horizons.
- **Horizons:** next school day, next 7 school days, next 30 school days (weekdays, as in `src.forecasting`).
- **Forecast origin:** the day after the last recorded date (20 December 2024), not today. Every result page states: "Forecast generated from available development data ending 20 December 2024."
- **Planning output:** predicted demand and recommended preparation (predicted demand + rule-based safety buffer, capped at 20%) are shown separately. The buffer is described as a heuristic, not a confidence interval. Risk (Low/Moderate/High) follows the buffer size. Cost is predicted meals × the recent average cost per meal. An optional capacity comparison reports shortage/surplus.

## 7. Security measures implemented

- Django authentication; `LoginRequiredMiddleware` on every page except login; POST-only logout.
- CSRF protection on all forms (tested: a POST without a token returns 403).
- Upload limited to users with the upload permission; Admin limited to staff; audit records are read-only in Admin.
- Secret key, debug mode, allowed hosts and database come from environment variables. With `DJANGO_DEBUG=False`, startup fails if the secret key or allowed hosts are missing, and secure cookies are on.
- Error pages never show stack traces. Artifact errors shown to users contain no file paths.
- Uploads: `.csv`/`.xlsx` only, 10 MB limit, sanitised stored filenames, stored under a git-ignored folder that is never served over HTTP.
- Role groups (School Manager, Resource Planning Stakeholder, System Administrator) are not yet implemented.

## 9. Dataset status

- **Active dataset (19 October 2026):** the anonymised Food4Education Google Sheet, read live via `BITETRACKER_GOOGLE_SHEET_URL` (5 schools; 722 usable school-day records, 2025-01-24 to 2025-11-03, after the 14-day lag window; target `daily_unique_students_tapped`). Pages show the Food4Education label and Model Performance shows "FOOD4EDUCATION RESEARCH RESULTS". Without the link (CI, tests) the synthetic dataset `data/sample/synthetic_school_meals.csv` is used and pages show "SYNTHETIC DEVELOPMENT DATA".
- **Active model (19 October 2026, Food4Education Google Sheet):** tuned XGBoost, selected by the lowest mean TimeSeriesSplit validation MAE (75.92; standard deviation across folds 13.49). Single held-out test evaluation: MAE 51.64, RMSE 88.80, R² 0.989. Persistence baseline test MAE 39.07; 7-Day Historical Mean test MAE 58.10. **The selected model does not beat persistence.** Linear Regression (78.49) and Random Forest (79.23) were within one fold standard deviation on validation MAE. R² is not an accuracy percentage. (The 6 October migration run used the synthetic dataset and selected Random Forest with validation MAE 55.43.)
- **Food4Education data:** loaded read-only from the Google Sheet by `src/google_sheet_loader.py`; not committed. Weather, cost and exam/event fields are not in the sheet and are held constant.

## 10. Deployment status

**Not deployed.** The application is deployment-ready in configuration only: environment-based settings, WhiteNoise static files, a WSGI/ASGI entry point, gunicorn tested locally, and custom error pages. `check --deploy` leaves two warnings (HSTS, SSL redirect) that depend on the hosting setup and can be switched on with environment variables.

## 11. Limitations to report

1. All results are synthetic and say nothing about Food4Education or real-world accuracy.
2. Forecasts start after 20 December 2024, and the synthetic calendar marks the following days as a holiday, so short-horizon demo forecasts are low (for example about 4 meals for SCH001 on day 1).
3. **Existing preprocessing runs before the train/test split** (unchanged by the migration):
   - per-school forward/backward fill and median imputation use the full history;
   - IQR outlier capping of `meals_served`, `leftover_meals` and `enrolled_students` uses full-history quartiles, so test targets are capped and test-period values influence training rows;
   - TimeSeriesSplit folds split by row position, so a date can be split across schools within a fold (the main train/test split does respect date boundaries).

   These are leakage risks in the reported synthetic metrics. Fixing them requires retraining and would change the reported numbers, so they are documented rather than changed.
4. Training uses observed weather as a perfect forecast.
5. Multi-day forecasts are recursive, so error compounds.
6. The safety buffer and risk levels are heuristics.
7. Roles are not implemented as groups; uploads are not reviewed or merged into training data.
8. Single-school capacity comparison only; the multi-school allocation and comparison pages were deferred.
9. Bootstrap and Plotly load from a CDN, so pages need internet access to render fully.
